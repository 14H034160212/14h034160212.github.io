不用预训练，在 16GB 显卡上用 LayoutLMv3 处理长文档

LayoutLMv3 和 ERNIE-Layout 最多只能读 512 个文本 token。订单或者带很多明细行的发票，一页往往超过这个长度，第 512 个 token 之后的内容模型根本看不到。在下面三个真实数据集上，截断到 512 会让模型看不到 41% 到 58% 需要标注的词。

结论：不额外预训练，让模型读完整页，三个数据集上 F1 都提高 20 到 33 分。16GB 显卡就能跑：读 2048 个 token 推理只要 0.80 GB 显存，512 时是 0.69 GB。

结果

每个模型都在每个数据集上按常规方式微调（2000 步，5 个随机种子）。三列之间唯一的区别是怎么处理超过 512 个 token 的内容：直接截掉（基线）、切成互相重叠的 512 窗口分别读，或者扩展模型的位置一次读完。

  • 读完整页遥遥领先。滑动窗口和扩展后的模型都比 512 基线高 20 到 33 分，5 个种子无一例外。
  • 滑动窗口还是一次读完？两者很接近。LayoutLMv3 一次读到 2048 个 token，在订单和发票上比滑动窗口高约 1.2 到 1.6 分，在登记表上两者打平。ERNIE-Layout 在三个数据集上都打平。滑动窗口最简单，不用改模型。
  • 发票对所有方法都很难（明细表格密集、OCR 有噪声），所以分数整体较低。

数据集：Google 的 VRDU，包括电视广告订单和美国登记文件；以及 RealKIE 的 FCC Invoices，370 张真实发票，每张好几页，许可证为 CC BY-NC 4.0。常用的发票、收据数据集（如 FATURA、SROIE）太短，测不出差别：它们没有任何标注在 512 个 token 之后。

怎么做到的：两处小改动

1. 让模型能读 512 个以上的 token。模型学过 512 个位置向量，每个位置一个。我把它们重复使用：第 513 个位置用第 1 个位置的向量，依此类推，然后照常微调。这是 Longformer 用过的办法。它之所以有效，是因为模型还能靠每个词在页面上的位置、以及词与词之间的距离，把重复的位置区分开。不需要预训练，微调也不会变慢：读完整页的模型在每个评估点都领先基线，只用四分之一的训练步数就超过了基线的最终分数。

2. 把显存降下来。LayoutLMv3 在每一层都会根据两个词之间的距离，给每一对词加一个分数。标准实现会为每一对词计算这个分数，中间用到很大的临时数组；长页面上占满显存的正是这些临时数组，而不是文本本身。这个分数只取决于距离，而距离只有几千种可能。所以我按距离预先算好、查表取用，并在各层之间共用。结果和原模型完全一样：在真实数据上，我比较的四种实现给出了相同的 F1，每个词的预测也都相同。

在 2048 个 token、批大小 2 下训练，开梯度检查点只要 4.0 GB，4096 个 token 也只要 6.7 GB。每个批次只补齐到其中最长的页面，所以短页面的开销和原来一样。在订单数据上用 2048 训练，总时间是基线的 1.5 倍，而不是 4 倍。

没有帮助的做法

  • 把位置拉伸而不是重复（位置插值），效果差 0.7 到 1.4 分。它会改变每个词的位置，连短页面也不例外，模型学到的东西就丢了；损失最大的正是 1024 个 token 以内的页面。
  • ERNIE-Layout PyTorch 移植版自带的长序列版本（旋转位置编码）掉到了 28 分，因为它丢弃了学到的位置。
  • ERNIE-Layout 改成右补齐（和原版 PaddleNLP 一样），微调后的准确率和移植版默认的左补齐相同。

给想深入了解的读者

V100。我是在 A100 上限制 15 GB 显存、只启用 V100 支持的内核测得的，不是在真正的 V100 上。查表版本用的是 PyTorch 自带的显存高效注意力，会用到 V100 的张量核心。我也试了 FlexAttention，它在 8192 个 token 时显存仍几乎不涨（0.87 GB），在 A100 上也很快；但它用 Triton 编译，而 Triton 已不再使用 Ampere 之前显卡的张量核心，所以不推荐在 V100 上用。

哪些是新的。重复使用位置编码（Longformer，2020）、用稀疏注意力把模型转成长文本版本（LSG，2022）、不训练就扩展 embedding 模型（LongEmbed，2024）、精确的相对位置注意力内核（arXiv 2611.01182，2026）都已经有人做过。我没在别处见过的，是面向版面模型的这套组合：支持它们的一维和二维位置分数、不预训练、注意力精确、只用能在 V100 上运行的 PyTorch 自带内核，并在真实长页面上验证。
