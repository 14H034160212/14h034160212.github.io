从字节出发，让 Qwen3.5 在 vLLM 上解码更快

视觉语言模型从文档里抽取字段时，大部分时间花在一个 token 一个 token 地写答案上。每个解码步都要把模型的全部权重读一遍，所以在 GPU 上，每步时间约等于权重字节数 ÷ 显存带宽。我以此为起点，从配置一路往下查到内核：每步读了什么、哪些内核读得慢、怎样在不掉精度的前提下少读字节、少生成 token。

实验设置：Qwen3.5-9B，用 vLLM 的在线 FP8 量化和它自带的 MTP 投机解码，跑在一张和其他任务共享的 A100 80GB 上。数据是公开的 nanonets/nn-auto-bench-ds 全部 1000 份文档（发票、收据、银行流水、护照；MIT 许可）：输入图片，按要求的字段输出 JSON，用字段级 F1 评分。延迟取 50 个单请求的 p50；吞吐是 16 个并发请求跑完全部 1000 份。所有精度比较都是按文档做的配对 bootstrap。

时间花在哪

请求时间的中位数是 935 ms，其中预填充（含视觉编码器）约 113 ms，解码 824 ms（88%）。CPU 上的图像预处理单独计时另需 42 ms。不开投机解码时，一个解码步 8.4 ms，GPU 有 99% 的时间在忙，所以问题不在启动开销。每步要读 8.95 GB 权重（6.9 GB 的 FP8 线性层加 2 GB 的 BF16 lm_head）。A100 实测拷贝带宽 1.75 TB/s，对应的下限是 5.1 ms，模型只跑到了它的 62%。

nsys trace 显示 8.4 ms 里有 6.1 ms 是 FP8 GEMM。A100 没有 FP8 张量核，所以 vLLM 用 Marlin 内核以"weight-only"方式运行 FP8 权重，边算边转成 BF16。在 CUDA graph 里逐个形状计时，这些 GEMM 平均只有 1.14 TB/s，而同样形状的 BF16 cuBLAS 能到 1.5–1.7 TB/s。

Marlin 的一个 bug：小层比大层还慢

有一个形状很突出。Qwen3.5 的 24 个 Gated DeltaNet 层各有一个 in_proj_ba 投影，从 4096 维只输出 64 维。Marlin 算它要 37 µs（int4 权重要 45 µs），而 BF16 只要 6 µs，4096 × 4096 的 Marlin GEMM 也才 14 µs。N 越小反而越慢。

原因在启动方式。Marlin 总是每个 SM 启动一个块（A100 上是 108 个）。只有一个输出 tile 时，每个块大约只分到一个 K tile，然后这些块要通过一把锁一个接一个地累加部分和，这条链有多长，耗时就有多长。vllm#69231 在输出 tile 很少时限制 K 方向的切分份数，更大的问题仍然用满整个 grid：

权重，K × N修复前修复后
FP8，4096 × 6437.2 µs9.3 µs
int4 g128，4096 × 6445.1 µs10.7 µs
int4 g128，4096 × 25620.6 µs11.3 µs
更大的形状（4096 × 4096 到 4096 × 24576）不变

端到端 p50 降低 3.8–4.7%，F1 不变。另一位贡献者在 GB10（48 个 SM）上独立复现了提速，并指出那里有一个形状看起来变慢了。我打印了 Marlin 的 tile 选择，发现那个形状有 4 个输出 tile，在 48 个 SM 上不会触发这个限制，差异只是噪声。

更好的 weight-only 内核：Humming

vLLM 维护者计划用 Humming 取代 Marlin（#65560）。在 A100 上，它在这个模型的每一种 GEMM 形状上都更快（全部 FP8 GEMM 每步从 6.12 ms 降到 5.19 ms；64 维那一层从 38 µs 降到 10 µs），整个解码步从 8.41 ms 降到 7.49 ms。在九种设置（输入/输出长度 × 并发数，每个后端两个服务器）的 serving 对比中，其中八种的输出吞吐是 Marlin 的 1.09–1.20 倍（并发 1、只输出 1 个 token 的那一种是 0.98，在重复测量的波动范围内），GSM8K 准确率不变（0.860 对 0.862）。compressed-tensors checkpoint 的 weight-only FP8 本来就优先选 Humming，但在线 --quantization fp8 仍然落到 Marlin。vllm#69242 让它也从 weight-only 内核表里选，并修复了一个标志位：它会让反量化函数把 Humming 重新打包过的权重当成原始权重读（对 [256, 512] 的权重返回了 [1024, 32]）。

草稿模型的 lm_head

开 MTP 时，草稿模型每生成一个草稿 token 都要复用目标模型 2 GB 的 BF16 lm_head，4 个草稿 token 就是每步读 4 遍。vLLM 可以给草稿模型一份量化副本（draft_lm_head_quantization），目标模型仍然用自己的 head 验证，所以输出不变。NVFP4 副本在 3 个草稿 token 时把 p50 降低 15.6%，4 个时降低 18.8%。FP8 副本在没有 FP8 GEMM 的 GPU 上无法启动；vllm#69177 让它在这些 GPU 上走 weight-only，并修复了一个缺失的布局标志，它曾导致 Humming 在这里崩溃。

少读字节，前提是精度不掉

4 bit 权重要读的字节约为 FP8 的一半，但精度必须守住。每一行都和用同样方式运行的 FP8 模型比较（GPTQ 那一行输出单行 JSON，见下文）：

哪些层用 4 bitp50（FP8 → 4 bit）ΔF1 [95% CI]
全部线性层，NVFP4 直接舍入873 → 749 ms−0.026 [−0.033, −0.018]
全部线性层，用公开数据校准的 GPTQ int4749 → 614 ms−0.018 [−0.024, −0.010]
只有 MLP 层用 NVFP4，其余保持 FP8873 → 755 ms+0.003 [−0.003, +0.009]

在这个模型上，注意力层和 Gated DeltaNet 的投影层对 4 bit 很敏感，GPTQ 校准之后也一样；int4 的目标模型还把 MTP 接受率从 0.86 拉低到 0.79。MLP 占线性层权重的 70%，量化起来很干净。vLLM 的在线量化可以在加载时用 quantization_config.targets 做这种拆分；匹配规则只能命中线性层，否则注意力模块也会被匹配到，加载就会失败。把目标模型自己的 lm_head 量化成 FP8 没有帮助：草稿模型的 NVFP4 副本要求目标 head 是 BF16，而让草稿模型共享一个 FP8 head，每步多读的字节比省下的还多。

少生成 token

模型输出的是放在代码块里、带缩进的格式化 JSON：每份文档 244 个 token，同样的 JSON 写成一行只要 179 个。在 prompt 里要求输出不带代码块的单行 JSON 后，输出降到 174 个 token。MTP 接受率随之下降（缩进最容易猜），所以实际收益比 token 数少一些，但 p50 在 4 个草稿 token 时仍降低 14%，5 个时降低 18%，这里 F1 不变。我之前在另一个发票数据集上见过紧凑格式掉精度，所以每个任务都需要自己验证。

还剩什么

即使是最好的配置，每步也只用到带宽下限的 64–70%，内核还有空间。这里的数字都来自 A100；在带宽更低的 GPU 上，同样的字节节省应该更重要，而在有原生 FP8 的 GPU 上，Marlin 和 Humming 这部分不适用。下一步是在其他架构的 GPU 上测出同样的表。

局限

一个模型，一张和其他任务共享的 GPU，两个公开数据集。在共享的 GPU 上，16 并发吞吐在相同配置的重复运行之间最多相差 7%；p50 的差异小于 0.5%。
