三个只给出错误结果、不报错的推理框架 bug

这周我修了三个推理框架的 bug：一个在 vLLM，两个在 ONNX Runtime。其中两个不报错也不警告，只是悄悄输出错误的数值；第三个会让图优化器在一个完全合法的模型上崩溃。每个修复都很小，8 到 30 行。大部分工作花在把问题范围不断缩小，直到原因一目了然，再证明修复只改变了该改变的东西。三个 PR 都在审核中。

1. vLLM：FP8 RMSNorm 在错误的地址读取跨步输入

vLLM 的一个 issue（#67411）报告：当输入的最后一维不连续时（比如转置过的张量），fused_add_rms_norm 会算出错误的值。内核按 input_stride * token + feature 读取输入，这默认了 input.stride(-1) == 1。C++ 主机代码对 residual 检查了这一点，对 input 却没有。

动手修之前，我先看了同一文件里的兄弟函数。rms_norm 会先把这种输入转成连续的；两个静态 FP8 版本 rms_norm_static_fp8_quant 和 fused_add_rms_norm_static_fp8_quant 则完全没有检查。在 main 上每种情况单独一个进程运行：

函数转置输入隔列取的输入
rms_norm_static_fp8_quantCUDA error: misaligned address4096 个输出错 4027 个
fused_add_rms_norm_static_fp8_quant错 4001 个，residual 也错错 3995 个，residual 也错

misaligned address 比算错还糟：它会让 CUDA 上下文无法再用，这个进程之后的所有 CUDA 调用都会失败。在我验证修复的时候，另一位贡献者为 #67411 中 fused_add_rms_norm 的部分开了 PR，所以我把 FP8 内核的问题单独报成一个新 issue，PR 只修这两个函数。它们只读输入，所以修复方法是在需要时把输入复制成连续内存，和 rms_norm 的做法一样（vllm#67484）。新测试在原代码上失败、修复后通过，977 个 layernorm 测试全部通过。一位社区成员还在另一张 SM80 显卡上独立验证了这个修复。

2. ONNX Runtime：Cast 优化器遇到 Where(c, x, x) 崩溃

onnxruntime#34192 给出了一个让 PropagateCastOps 优化器崩溃的三节点模型：一对 FP16→FP32→FP16 的 Cast，结果同时连到 Where 的两个数据输入。优化器删掉这对 Cast，把下游节点的输入边移到原始张量上。它用 IndexOfNodeInput 找这个输入，而这个函数只返回第一个匹配的位置。于是它只删除、重连了第一条边，却把所有匹配的输入定义都替换了。连到第二个输入的那条边仍然指向已删除的 Cast，后面清理时就报错 Argument mismatch when removing edge。

同样的写法还出现在另一条代码路径里（第一个 Cast 还有别的下游节点时），那条路径报的是另一个错误：Can't remove node ... as it still has output edges。修复后，两处循环都会遍历下游节点每一个用到被删除张量的输入（onnxruntime#34221）。新测试覆盖两种图结构、两种传播策略和三个优化级别，在 main 上分别以这两种异常失败，修复后通过；793 个优化器测试仍全部通过。

3. ONNX Runtime：scale 不是常量时 MatMulNBits 输出全零

onnxruntime#34216 报告：一个 FP16 的 DequantizeLinear 接 MatMul，开启图优化后结果从 0.25 变成 0。优化后的图透露了原因：两个节点被融合成 accuracy level 4（int8 路径，也是默认值）的 MatMulNBits；CPU 为了让它在 FP32 下运行，又给 FP16 的 scale 插了一个 Cast。有了这个 Cast，scale 就不再是常量了。

这启发了一个完全不含 FP16 的测试：一个 FP32 的 MatMulNBits，scale 分别是常量或者图输入。在发布版 onnxruntime 1.31.1 上：

scaleaccuracy level 1accuracy level 4
常量正确正确
图输入正确全零
Cast 的输出正确全零

所以这个 bug 和 FP16 无关：在 x64 上，任何走 int8 路径、scale 或零点在运行时才给出的 MatMulNBits 都输出全零，4-bit 和 8-bit 权重都是，1.29、1.30、1.31 三个版本也都是。x64 的 int8 内核从预打包的权重里读 scale，而预打包只能用常量 scale。ARM64 已经会在这种情况下跳过预打包，修复就是把这个现成的检查推广到 x64（onnxruntime#34224）。现有的 x64 动态 scale 测试强制走了 FP32 路径，所以 int8 的情况一直没被覆盖。

有一次端到端验证一开始误导了我：用全部优化级别运行 issue 里的模型，没有修复也能通过。原因是在 ORT_ENABLE_ALL 下，后面的优化会把插入的 Cast 常量折叠掉，scale 又变回常量。issue 用的是 ORT_ENABLE_EXTENDED，在这个级别下，main 输出 0，修复后输出正确的 0.25。

有用的做法

  • 检查被报告函数的兄弟函数。vLLM 里，被报告函数旁边有两个函数缺同样的检查，其中一个会让 GPU 上下文崩溃。ONNX Runtime 里同样的循环出现在两条代码路径上。
  • 不断去掉变量，直到 bug 依然存在。MatMulNBits 的问题看起来像 FP16 舍入问题。去掉 FP16 后 bug 仍在，才发现真正的原因是运行时 scale，影响的模型多得多。
  • 证明测试在修复前失败，而且是因为正确的原因。有两次，我的第一次检查在未修复的代码上也通过了：一次是测试被条件编译排除在外，一次是更高的优化级别掩盖了 bug。两次如果只看第一次的结果，都会得到误导性的证据。
  • 开 PR 前再查一次有没有人在做。三个 issue 中有一个，在我准备好时已经有人开了 PR。把我的改动缩小到对方没覆盖的部分，两个 PR 就都有价值。
