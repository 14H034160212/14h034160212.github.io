标注还是生成？在同一批文档上把两者都微调

在之前一篇文章里，微调过的 Qwen3.5 词级标注模型远远好于零样本的 JSON 生成。但那个比较混了两件事：标注对生成，以及训练过对没训练过。这次两者都在同样的 801 份文档上微调，在同样的 199 份文档上测试。结果是标注模型不再是最准的，但仍然快了约十倍；只把它最没把握的文档交给生成模型，可以兼得大部分好处。

数据是公开的 nanonets/nn-auto-bench-ds（发票、收据、银行流水、护照；MIT 许可），共 1000 份，按文档类型用固定随机种子分成 801 份训练、199 份测试。评分是被询问字段的字段级 F1。标注模型的标签来自把每个标准答案在数据集自带的 OCR 词里做归一化字符串匹配（95.5% 的值能找到，其余不标），得到 54 种字段名的词级 BIO 标签。所有实验都在一张和其他任务共享的 A100 上；精度差异都是按文档做的配对 bootstrap。

两个模型

  • 生成：Qwen3.5-9B，QLoRA（r = 16，600 步，35 分钟），训练它对推理时同样的 prompt 输出单行 JSON。部署时把 adapter 合并进原始 BF16 权重文件，保留 MTP 草稿模型的权重，再用解码那篇文章里最快且不掉精度的配置运行（MLP 权重 NVFP4、其余 FP8，在 Humming 内核上 weight-only；MTP 4 个草稿 token，草稿 head 用 NVFP4）。
  • 标注：Qwen3.5-0.8B 或 2B，加 LoRA，在每个 OCR 词的第一个子词上接一个线性分类头（2000 步；0.8B 用 43 分钟，2B 用 54 分钟），用 vLLM 的 pooling runner 一次前向完成。

结果

方法p50p95批量 份/秒F1（199 份测试文档）
生成，9B 零样本668 ms818 ms6.00.680
生成，9B 微调663 ms748 ms6.50.882
标注，2B 微调72 ms88 ms16.90.857
标注，0.8B 微调68 ms95 ms18.30.841

以上是 vLLM 离线运行的结果；延迟是单个请求的 p50 和 p95，吞吐是全部文档一起跑（生成时同时 16 个请求）。标注模型用了下文的 1 百万像素上限。

微调让生成模型的 F1 提高了 20 个点，速度没有变慢。MTP 草稿模型没有跟着重新训练，但接受率只从 0.86 降到 0.84，而且微调后的模型输出更短（157 个 token，原来 193 个）。微调过的 2B 标注模型比它低 2.6 个点（95% CI −4.5 到 −0.8），单请求延迟约为它的九分之一。2B 标注模型比 0.8B 高 1.5 个点（CI +0.2 到 +3.0），只慢几毫秒。

一张 1950 万像素的页面

一开始 2B 标注模型批量处理每秒只有 3 到 4.5 份，比一份一份地发还慢。原因不是图像预处理（单个 CPU 线程每张 32 ms，开并行 renderer worker 也没用），也不是 vLLM 的多进程引擎。引擎大部分时间都在等 GPU。前 80 份测试文档每秒能跑 38 份，其余平均每份 150 ms。数据集里有几张图非常大：一张 1950 万像素（64,896 个视觉 patch，16,224 个图像 token），有一类文档平均 530 万像素，而这些页面只有大约 150 个词。视觉注意力的开销随 patch 数平方增长，所以这几页拖慢了整个批次。

推理时把图像限制在 1 百万像素（mm_processor_kwargs={"max_pixels": 1048576}），模型不变（仍是全分辨率训练的那个）：

标注模型份/秒 之前 → 之后ΔF1 [95% CI]
0.8B8–10 → 18.3−0.001 [−0.006, +0.003]
2B3–4.5 → 16.9−0.001 [−0.006, +0.004]

生成那边本来就把图片长边缩到最多 1280 像素，所以一直没遇到这个问题。把 max_num_batched_tokens 从 8192 提到 32768 也让不限像素的 2B 快了 40%，但真正解决问题的是像素上限。

只把没把握的文档交给生成模型

标注模型的概率能说明它什么时候没把握。我把一份文档的置信度定义为：它预测出的字段的词、以及没被标注的词里，最高类别概率的最小值。低于阈值的文档再交给生成模型，用生成模型的答案。阈值用测试文档上的 2 折交叉验证选（20 次随机划分，最常选中 0.7），所以精度估计不是在被评分的文档上调出来的。这样大约 35% 的文档会被转走。

然后把它当成服务真正跑起来：微调过的 9B 在一张 GPU 上用 vllm serve 提供服务，2B 标注模型和路由在另一张 GPU 上；两边都关掉了前缀缓存和多模态缓存，保证没有请求能从缓存里拿结果：

方法逐份处理：p50p95平均批量 份/秒F1
只用生成（9B 微调）590 ms735 ms607 ms6.60.882
只用标注（2B，1 百万像素）72 ms90 ms78 ms21.10.857
先标注，35% 再生成72 ms767 ms291 ms10.00.870

路由把平均延迟降了一半，三分之二的请求和标注模型一样快。代价是比全部生成低 1.2 个点，在交叉验证的估计里属于噪声范围（−1.1 个点，不显著）。这个演示里批量的两个阶段是先后跑的；如果两张 GPU 同时工作，生成模型只需要承担 35% 的流量。另一种做法是保留标注模型有把握的字段、只从生成模型拿其余字段，它比全部生成还高 1 个点，但要转走约 80% 的文档，所以它换来的是精度而不是速度。

一个测量陷阱

我最初测的标注模型延迟低了 20 到 25 ms。脚本在吞吐测试之后，用刚处理过的文档测单请求延迟，vLLM 的前缀缓存省掉了大部分前向计算。199 个标注请求能全部放进缓存；1000 份文档的生成测试放不下，所以在没见过的文档上重测时，之前发布的数字基本不变（933、859、670 ms，对比发布的 939、873、678 ms）。测单请求延迟要用引擎没见过的文档，或者关掉缓存。

该用哪个

  • 要最高精度：微调生成模型。在这个数据上它最准，速度和零样本一样。
  • 要最低延迟或成本：用标注模型，并限制像素。它需要词级标签，只能覆盖在 OCR 文本里原样出现的值和训练时见过的字段名。
  • 两者都要：先标注，没把握的再生成。

局限

一个公开数据集、199 份测试文档，标签由字符串匹配得到，一张和其他任务共享的 GPU（p95 是这里噪声最大的数字）。生成模型的延迟是在数据集前面的文档上测的，其中有些是训练文档；这会影响那些文档上的精度而不是速度，精度只在测试文档上报告。
